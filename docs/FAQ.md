# The project

## Walk me through what you built and why you set it up that way.

It was my refresher for today — I wanted something tangible rather than talking
about SFT in the abstract.

I needed a task that was **objectively verifiable, non-trivial, and fast to
iterate on**. I considered text-to-SQL but everyone does it, and verification
needs a database round-trip that would have slowed the loop. Regex gives you a
free oracle: you just *run* the pattern.

So: 76 concepts across three families — **validate** (accept/reject strings),
**extract** (capture a substring), **substitute** (pattern plus replacement) —
plus a taxonomy of ten conversational moves for multi-turn, where the user
refines the regex: narrow, broaden, repair, rollback and so on.

The key design decision: **the prompt shows the model only two or three example
strings, but it's scored on a larger hidden set it never sees.** So a model that
copies the examples instead of reading the instruction passes the prompt and
fails the score. Overfitting becomes a measured number rather than a suspicion.

The dataset is fully synthetic, generated by Opus — so in one sense this is also
task-specific distillation of a frontier model. And the result surprised me,
which I'd like to get to.

## Isn't the hidden set just a test-set holdout?

No — they catch different failures, and a standard holdout is blind to this one.

A train/test split tests **across tasks**: can it handle a task it never trained
on? The hidden set tests **within one task instance**: did it read the
instruction, or copy the demonstration in front of it?

Concretely: a semver task from the test split shows four positives and four
negatives, none of which has a leading zero. The model answers
`\d+\.\d+\.\d+` — which satisfies all eight shown strings. Score it on those
eight and it gets 100% on a properly held-out task. It's still wrong, because
the instruction says no leading zeros. The hidden set catches it.

I can only do this because **the model's output is a program**. I don't compare
output strings to a reference — I run the regex on inputs that appear nowhere in
the prompt. You can't do that with a summary or a translation.

It's measuring **in-context overfitting** rather than training-data overfitting.
Everyone guards the second; almost nobody measures the first. For my tuned
Instruct model it's 15% of test items.

## The dataset is synthetic. How do you know any of it is correct?

Every gold answer is **executed, not trusted** — run against both the visible and
hidden string sets, for every spec in every split. And it's a build gate: if a
gold fails its own test set, the dataset doesn't get written.

It caught a real one. I'd filed `Pw0rd!aa` as an invalid password — it's exactly
8 characters with a lowercase, uppercase, digit and special, so it satisfies
every rule. Had it shipped, every model would have been marked wrong for being
right, on a training item.

But I'd flag the limit myself: execution proves the pattern is **consistent with
the strings**. It doesn't prove the instruction is unambiguous, and the
instruction and the strings came from the same model as the answer. So it's
internal consistency, not external correctness. The mitigation is a human
spot-check on a stratified sample, which I didn't have time for overnight and is
in my limitations section.

And the **reasoning traces are a different story** — I authored those knowing the
answer, so they're rationalisation rather than verified reasoning. Rejection
sampling would fix that and it's the first thing I'd change.

## Should I be convinced by the 21-point multi-turn result?

Partly. Here's what I'd defend and what I wouldn't.

**Solid:** it's a paired comparison on the same 90 turns, McNemar χ²=7.90,
p<0.05. And the mechanism is visible in the degradation — Instruct drops 15.6
points when it reads its own output, Thinking drops 4.5. Same items, only the
history differs. It replicates turn by turn: 80→47→27 against 87→77→53.

**Wouldn't claim:** n=90, so the interval is wide. It's scoped to free-running
multi-turn — on single-shot they tie, and Instruct actually *wins* on the harder
standalone tasks, 55.7 to 40.0. And there are **no hard-tier items in the
multi-turn set at all**, so I don't know whether the effect survives on harder
problems. That's untested rather than optimistic.

One thing cuts the other way: Thinking was still improving on dev when I stopped
it, so 21 points is a **floor**, not an optimistic number. And I can't fully
separate "reasoning helps" from "Thinking trained on 2.5× the target tokens" —
that confound is inherent to the treatment.

## What's the actual finding, in one sentence?

The reasoning trace isn't an accuracy upgrade — it's **error recovery**. Instruct
pattern-matches its previous answer forward so an early mistake propagates;
Thinking re-derives from the instruction each turn. The effect is invisible under
teacher-forced evaluation and only appears when the model consumes its own
output.

# SFT fundamentals

## I hand you a 7B base and 50k instruction pairs. Walk me through the setup.

First I'd ask: what domain, what does the base already do badly, and is the 50k
curated or scraped? That changes the answer a lot.

**Data first.** Dedup including near-dups, check output-format consistency, look
at the length distribution, and split by source or topic rather than randomly so
near-duplicates don't leak into the eval set. With 50k pairs, **data quality
dominates any hyperparameter I could pick** — LIMA got competitive results on a
thousand curated examples.

**Method.** LoRA. 50k is task adaptation, not teaching new knowledge, and I get
cheap training plus swappable adapters. Full fine-tuning only for a large domain
shift or much more data. Rank 16 to start, targeting attention plus the MLP
projections; raise the rank only if it underfits.

**Hyperparameters.** LR 1e-4 cosine to zero with a short linear warmup, alpha 2r,
dropout 0.05, effective batch 32–64, one to three epochs — past that you're
memorising. bf16. Loss masked to responses only so it doesn't learn to generate
user turns, and I'd verify the mask by decoding it rather than trusting the
library.

**Eval.** A held-out task metric, and select checkpoints on that rather than
validation loss. Plus a regression check on a general benchmark, because
specialising an assistant is exactly where catastrophic forgetting bites.

## Why mask the prompt tokens?

You only want loss on the model's reply. Train on the prompt and you're partly
teaching it to generate *user* turns, and your loss becomes dominated by text you
don't care about. Set prompt labels to `-100` — PyTorch's ignore index.

The failure worth knowing: **a mask bug is invisible in the loss curve.** The
number goes down happily whether or not the mask is right. If you don't train the
EOS token the model never learns to stop. The only defence is decoding the mask
and reading it, which is why I dumped mine token by token.

## It shipped, and a week later general chat is worse. What happened?

First — do we have a **before-number**? If we never benchmarked general capability
pre-ship I can't distinguish regression from perception, and that's a process gap
to fix regardless: a regression suite should gate any checkpoint.

Then scope it: broad, or one area? And rule out the cheap explanation first — a
chat-template or sampling mismatch at serving time looks identical to forgetting.

If it is genuine forgetting, **LoRA gives me options before retraining**: roll
back to an earlier checkpoint, scale the adapter down at inference, or simply
don't apply it for general queries. The base weights are untouched, so I can
unplug it. That buys time.

The durable fix is **replay** — mix general instruction data back into training,
lower the LR or epochs, and put that general data in dev and test so I'm
selecting checkpoints on both axes, not just the domain one.

## Why not select checkpoints on validation loss?

On short structured targets the loss is dominated by boilerplate the model fits
immediately, so it can keep falling while task accuracy declines. Mine did
exactly that — Instruct's loss went 0.0006 → 0.0003 between epochs 2 and 3 while
dev accuracy fell from 62.1% to 60.9%. **Loss-based selection would have picked
the worse checkpoint.** With a free verifier there's no reason to use a proxy.

## SFT vs DPO vs RLHF — when do you need which?

SFT takes (prompt, good answer) and teaches format, task and domain behaviour.
DPO takes (prompt, chosen, rejected) and teaches preference between two plausible
answers. RLHF/PPO does the same online with a reward model and a KL penalty to
the reference.

The standard pipeline is SFT **then** preference optimisation, because preference
methods need a policy that already produces reasonable candidates.

You need preferences when the complaint is *"the answers are all technically
correct but I want it to prefer this style, this level of detail, or to refuse
here."* SFT can't rank — it can only demonstrate.

# LoRA

## How does LoRA work?

Every targeted weight matrix gets a small side-channel: a down-projection to rank
16 and an up-projection back. Only those two train — the base weights are frozen.

The bet is that a **task adaptation is low-rank** — a structured change, not a
random rewiring — so you don't need millions of degrees of freedom to express it.

```
y = W·x  +  (alpha/r)·B·A·x
     ↑                ↑
   frozen      the only thing that trains
```

In my run that's 0.81% of parameters trainable and a **126 MB adapter instead of
an 8 GB model**.

## What are A and B, and why two?

**A reads** — it squeezes the 2560-dimensional input down to 16 numbers: *which
16 directions matter for what I'm learning?* **B writes** — it expands those 16
back to full width and adds them to the output.

Two, because the update `ΔW` must have the **same shape as W** to be added, but
you don't want W's parameter count. A product of a tall-thin and a short-wide
matrix gives exactly that:

```
(2560×16)·(16×2560) = 2560×2560     ← full shape
  81,920 parameters vs 6,553,600    ← 80× fewer
```

The 16 in the middle **is the rank** — everything the adapter learns has to
squeeze through it.

## What are alpha and r?

`r` is the rank — the bottleneck width, so it sets the adapter's capacity.
Typical 8–64.

`alpha` is a fixed scale on the adapter's output, applied as `alpha/r`. It exists
so you can change the rank without your effective step size changing underneath
you. Convention is `alpha = 2r`. Mine: r=16, alpha=32, so scale 2.

`alpha` is **not** a learning rate — it's baked into the forward pass and stays
there at inference.

## Why is B initialised to zero?

So the adapter contributes **nothing** at step 0 — `B·A = 0`, so `y = W·x`
exactly, and training starts from the pretrained model bit-for-bit. If both were
random you'd be injecting noise into every layer before learning anything.

**Why not both zero?** Then nothing ever moves. `∂L/∂A` is proportional to `Bᵀ`,
so it's zero when B is zero. `∂L/∂B` is proportional to `(A·x)ᵀ`, which is
nonzero because A is random. So B moves first, and once B ≠ 0, A starts getting
gradients too. **It bootstraps.** That asymmetry is the whole trick.

"Identity initialisation" means the *added term* is zero so the layer is
unchanged — not that B is the identity matrix.

## Added or multiplied?

**Added.** `W_effective = W + (alpha/r)·B·A`.

B and A are multiplied together to *form* the update, and it's scaled by a
scalar — but it's **added** to the base weights. That's what makes `B=0` a clean
no-op (multiplicative would zero out the layer), what makes merging trivial, and
what lets you dial the adapter down or turn it off.

## Does each layer get its own A and B?

Finer than that — each **targeted matrix** does. 36 layers × 7 projections = 252
independent A/B pairs, 504 tensors in the adapter file. The rank is shared at 16;
the outer dimensions match whatever matrix each pair adapts, so the KV
projections are smaller because of grouped-query attention and the MLP ones are
larger.

## Why is low rank enough?

Empirical, not a theorem. Measured weight updates from full fine-tuning
concentrate in a small number of directions, so a low-rank approximation captures
most of it. If a task genuinely needed more capacity you'd see it underfit, and
you'd raise the rank.

# Schedules and statistics

## What do warmup and cosine decay do?

**Warmup** ramps the LR up over the first few percent of steps. Adam's variance
estimates are unreliable at step 0, and one oversized step can knock a pretrained
model out of a good region — you'd spend the rest of training recovering.

**Cosine** decays to zero: big steps early to make coarse progress, small steps
late to settle into a minimum rather than bouncing around it. Like parking a car
— big movements to get near the space, small ones to line up.

Worth knowing: the schedule is planned for a **fixed step count**, so "just train
longer" isn't free — you'd re-plan and rerun, not resume. That's part of why my
Thinking model stopped improving where it did.

## Why a paired test?

Both models answered the **same 160 items**. Items both got right, or both got
wrong, carry no information about which is better — they cancel. Only
disagreements inform. A paired test is both correct and more powerful than
comparing two independent proportions.

## What's McNemar's formula?

```
      (|n01 − n10| − 1)²
χ²  = ──────────────────      compared against χ² with 1 df; 3.84 = p<0.05
          n01 + n10
```

where `n01` and `n10` are the two discordant counts. The `−1` is a continuity
correction, which makes it more conservative.

My tie: 18 vs 20 → χ² = 1/38 = **0.03**. My free-running result: 11 vs 30 →
χ² = 324/41 = **7.90**.

Under the null, each discordant pair is a coin flip, so you'd expect the two
counts to be equal. The test asks whether the imbalance is bigger than a fair
coin would produce.

## What is chi-squared with one degree of freedom?

**A standard normal, squared.** You take the imbalance, divide by how much it
would wobble by chance, and square it so direction doesn't matter. The "1" is
because you squared one thing.

The 3.84 threshold is just **1.96²** — the familiar 95% normal cutoff, squared.
So "χ² > 3.84" and "more than 1.96 standard errors from zero" are the same
statement.

χ²=7.90 is √7.90 = **2.81 standard errors**, which happens about 1 time in 200 by
chance. χ²=0.03 is 0.17 standard errors — a coin flip.

`p<0.05` means: *if the models were identical*, you'd see a gap this large or
larger less than 5% of the time. It is **not** "95% chance the result is real."

## Why aren't the per-move results reported?

n=6 per move. One item moves the rate by 16.7 points, and a 6/6 result has a 95%
interval of [61, 100] while 0/6 gives [0, 39]. Those overlap, so the ranking is
meaningless. The move balancing still mattered — it keeps the *training*
distribution even — but answering "which moves does SFT improve?" needs 5–10×
more test trajectories.

# Things to volunteer before being asked

1. **Thinking is under-trained** — dev still rising at epoch 3, so its numbers are
   a floor
2. **2.5× supervision confound** — can't cleanly separate reasoning from more
   target tokens
3. **Traces are authored, not certified** — rationalisation, not verified reasoning
4. **No untrained-Thinking baseline** — it doesn't terminate in an affordable budget
5. **Single seed**, no variance estimate
6. **Four bugs I found in my own results** — a 384-token cap measuring my config
   instead of the model; a parser grading the model's scratch work; 21 NARROW
   moves against 1 ROLLBACK passing every correctness gate; 24% duplicate prompts
